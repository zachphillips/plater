loop.whythe part no other CMS does

    

      
Some changes aren't words.

      
Every lightweight CMS can swap a headline. None of them can make three cards stack on mobile, because that isn't content — it's markup and CSS, and it lives in files the CMS was never allowed to touch. So it becomes a ticket, and the ticket becomes a month.

      
Plater routes it instead. The capture overlay records what you clicked with enough precision that an agent can find it again: the CSS selector, the element's own HTML, the visible text around it, the content key it binds if it binds one, the page URL, and the element's box on screen. You add a sentence. That package goes to a coding agent running against a real checkout of your repository.

      
The person who noticed the problem is the person who fixes it, in the place where they noticed it.


      
The trust boundary is the interesting part

      
The browser never holds a repository credential, and it never names a repository. It posts to your own origin, authenticated the same way saving is. That relay checks your credential again, overwrites the site field with its own configured name — so a request can't be aimed at someone else's repo — and only then forwards the note with a server-side bearer token.

      
The agent host maps site names to repositories on its own side, from a file you control. It is bearer-gated with a constant-time compare, rate-limited, concurrency-capped, and writes an append-only job journal. And it opens a pull request by default. A note produces something to review, not something to explain afterwards.


      
Design mode: pictures before code

      
When you don't know what you want yet, toggle design mode and the loop inverts. The host screenshots the live page, generates several concept images of the element redesigned, and hands them back to the overlay. You pick one. The chosen image becomes the specification — only then does a coding agent start writing, and it writes to match the picture you approved. Nothing is committed against a guess.

    

  







  

    
cms.modelthe substrate stays; the layer is thin

    

      
Your content is a JSON file in your repo.

      
There is no template language and no build step. You write ordinary HTML and mark the parts that are content. The markup you author is the fallback: if a key is missing, or JavaScript never runs, the page still renders exactly what you wrote. The site is never blank, never waiting on a fetch, and fully indexable before a single script executes.

  "home": {
    "hero": {
      "title": "Buildings that age well.",
      "sub": "A four-person studio…"
    }
  },
  "work": {

      { "name": "Alder Shed", "url": "/work/alder/" },

    ]

Saving is a commit, not a write

      
Add ?edit to any URL and every bound element becomes editable in place. Saving sends only the keys you changed. The handler fetches the current JSON from the GitHub Contents API, deep-merges your patch, and puts it back as a commit — which triggers whatever deploy you already had.

      
content: home.hero.title (via Plater)web/content/site.json · +1 −1 · main

      
That's the whole publish pipeline. There's no cache to bust, no CMS database that can drift from the repository, and no export path to worry about, because nothing was ever imported. git log is your edit history. git revert is undo. Delete Plater tomorrow and the site keeps working — it's still HTML and a JSON file.


      
Two credentials, both checked on the server

      
Sign in with Google — verified against Google's tokeninfo endpoint, checking audience, verified email, expiry, and your allowlisted address — or use a shared edit token compared in constant time. The token path exists because real editing happens on a phone at 11pm, and OAuth popups on a phone at 11pm are how edits don't get made. With no admin address configured, the handlers fail closed: nobody is authorized until you say who is. The GitHub token stays on the server, always.


      
Named drafts, not commit archaeology

      
Git remembers every save, but that's forensics, not editing. Versions are the editorial layer: named tracks of whole alternate drafts, one file per page. Call a track shorter or v2-launch — it exists as soon as a file is written. Add ?draft=shorter to a URL and the entire page renders from that track, in place, on the real site. Edits autosave to the draft. When you like it, Make this live promotes it as a normal commit.


      
Review state that expires by itself

      
On a multi-page site, edit mode shows a sitemap rail with a persistent reviewed checkbox per page. The record stores a hash of the page's HTML plus only the content keys that page binds — so any later edit or push automatically flips exactly the affected pages back to unreviewed, and nothing else. Checked means checked since it last changed.

    

  







  

    
standards.setplumbing the web already asked for

    

      
Everything a CMS owes the web. Nothing that tells you how to think.

      
No tags. No categories. No channels. No collections. A post is just a page somebody decided to put in the feed. One-off pages stay great, and nothing has to match anything else to exist. What Plater does ship is the boring, load-bearing plumbing that small sites skip and then regret.


      
    
        
  • /feed.xml + /feed.jsonfeed.js
    The feed is hand-curated content, not a database query. It's an array in your JSON — edit it the way you edit a page, reorder it by reordering it, point an item at any URL including someone else's site. Dates are stored once as RFC 3339 and emitted as valid RFC 822, so nobody hand-writes the web's most-fumbled date format. Item ids are permanent; readers dedupe on them.
    • 
        
  • /sitemap.xmlsitemap.js
    Built from the same page enumeration the review checklist uses, so it can't disagree with the site. lastmod appears only when a real review record backs it, never a fabricated timestamp. No changefreq, no priority — search engines ignore them, so shipping them is just lying politely.
    • 
        
  • Redirects & a real 404route.js
    Redirects are content: an array in the same JSON, live the moment the save deploys. The rule that follows is enforceable — renaming a URL means adding its redirect in the same change. The 404 page's copy is editable like any other page, and it returns an actual 404 status.
    • 
        
  • /api/manifest + /llms.txtmanifest.js
    The site, machine-readable: every page, the content keys each one binds, review freshness, the feed, and a self-describing write path — how to save, how to send a note, what the house rules are. An agent that finds a Plater site learns to edit it from one GET, without ever reading Plater's source.
    •

start.runsixty seconds, no signup

    

      
Try it in a minute.

      
There is nothing to install. Plater has zero runtime dependencies and zero dev dependencies — npm test is Node's own test runner, npm run lint is node --check.

      
# a whole site, running and editable, in one command
npm create platercms@latest my-site
cd my-site
npx platercms dev .
open 'http://127.0.0.1:4188/?edit'

      
Click any highlighted text, type over it, save. Locally that writes straight to the site's JSON file — commit it when you're happy. Deployed, the identical handler commits it for you.


      
Or read the source first

      
git clone https://github.com/zachphillips/plater
cd plater
npm run demo            # serves examples/static-site


      
Wiring a site you already have

      
npx platercms init .      # vendors the client, scaffolds api/, never overwrites
npx platercms doctor .    # tells you exactly what's still unwired

      
Three bindings, one toolbar, one initPlater call — the five-minute guide is the copy-pasteable version. The doctor command is the honest one: it inspects a site's wiring, prints the environment checklist, and names what's missing rather than failing at deploy time. The agent loop needs one more piece — a machine you own running the agent host, behind a tunnel. The repository's README walks through it.

Not built yet

          
    
            
  • The npm packages aren't published yet. They're built and named; the first tag publishes them. Until then, vendor from a checkout
    • 
            
  • The agent host is single-tenant by design. The bearer token is the whole security boundary
    • 
            
  • Google auth is one address, not a list. Multiple editors share the token
    • 
            
  • Design mode needs local tooling installed, with no graceful fallback when it's absent
    • 
            
  • Handlers are Vercel-shaped. platercms serve runs them anywhere, but only Vercel's rewrites are written down — Cloudflare Pages and Netlify aren't
    • 
            
  • Tests cover the server seams, not the browser overlay. There's no headless test of the editor in this repo
    • 
            
  • The old command name still works and should stop working at 1.0
    • 
          

        

      

      
Issues and pull requests are welcome. The bar for a change is the same as the bar for the codebase: no runtime dependencies, no build step, no framework. Continuous integration runs the linter and the tests on Node 20 and 22, and both have to pass.
